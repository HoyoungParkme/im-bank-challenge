# USECASE (Cockburn)

## 0. 이 문서의 형식

유스케이스마다 12행 표, 기본 흐름, 확장을 둔다. 확장 번호는 기본 흐름의 단계 번호에 글자를 붙인다(`3a.`).

ID의 글자는 주 액터의 종류를 뜻한다.

| 글자 | 주 액터 | 이 문서 |
|---|---|---|
| `H` | 사람 | UC-H1 ~ UC-H4 |
| `A` | 에이전트 | 없음 |
| `G` | 외부 시스템 | 없음 |
| `S` | 시스템. 하위기능이며 호출자가 있다 | UC-S1 ~ UC-S8 |

**A를 쓰지 않는 이유.** 이 제품의 AI 에이전트는 사용자 목표를 스스로 시작하지 않는다. [[IMBC-PRD-001#G2]]에 따라 에이전트는 화면 뒤에서 리포트를 만드는 엔진이므로 시스템 경계 안에 있고, 하위기능을 수행하는 주체로만 등장한다.

**G를 쓰지 않는 이유.** 상가(상권)정보 API, 지원사업 공고 API, 앵커 원장은 호출당할 뿐 먼저 유스케이스를 시작하지 않는다. 분기마다 스냅샷을 자동 갱신하는 스케줄러를 두면 G가 생기지만, 갱신 주기가 [[IMBC-PRD-001]] 미결사항에 남아 있어 두지 않았다.

**시나리오와의 관계.** [[IMBC-SCN-001#S4]](현장 시연)는 별도 유스케이스로 세우지 않았다. 시연자는 네트워크 없는 환경에서 예비창업자 역할을 대신 수행하는 것이므로 [[#UC-H1]]의 확장 1b로 흡수했다.

## 2. 사용자 목표 수준 유스케이스

#### UC-H1 창업 계획을 평가받는다

| 항목 | 내용 |
|---|---|
| 범위 | 창업 신용 리포트 엔진 |
| 수준 | 사용자 목표 |
| 주 액터 | 예비창업자 |
| 이해관계자와 관심사 | **예비창업자**: 자기 계획이 살아남을 가능성과 개선 방법을 알고, 그 결과로 은행 평가를 받고 싶다.<br>**심사역**: 넘어오는 리포트의 근거가 추적 가능하고 발급 뒤 고쳐지지 않았기를 바란다.<br>**iM뱅크**: 사업 이력 없는 고객을 놓치지 않으면서 부실 위험은 가려내고 싶다. |
| 사전조건 | 대상 지역의 현재 스냅샷과 코호트 비교용 과거 분기 스냅샷이 적재돼 있다([[#UC-S8]]). |
| 최소 보장 | 평가가 실패해도 근거가 부족한 수치를 담은 리포트는 발급되지 않는다. 입력한 조건은 남아 다시 시도할 수 있다. |
| 성공 보장 | 식별번호가 붙은 리포트가 발급된다. 생존 전망이 업종 기준선·경쟁 밀도 보정·지역 보정으로 분해돼 있고, 두 시점 생존곡선·개선 시나리오·지원사업 판정·기준일·한계 고지가 담긴다. |
| 트리거 | 예비창업자가 창업 계획의 평가를 요청한다. |
| 패키지 | 평가 |
| 포함(include) | [[#UC-S1]], [[#UC-S2]], [[#UC-S5]], [[#UC-S3]] |
| 확장점(extension point) | — |
| 일반화 | — |

**기본 흐름**
1. 예비창업자가 업종 대·중·소분류, 구·군과 행정동, 예산, 면적을 선택형 입력으로 고른다. 자유 텍스트 입력란은 없다.
2. 예비창업자가 평가를 요청한다.
3. 시스템이 입력 조건에 맞는 코호트의 생존을 집계한다([[#UC-S1]]).
4. 시스템이 예산 안에서 생존 전망을 올리는 개선 시나리오를 탐색한다([[#UC-S2]]).
5. 시스템이 지원사업 공고와 입력 조건을 대조해 자격을 판정한다([[#UC-S5]]).
6. 시스템이 결과를 리포트로 조립해 발급한다([[#UC-S3]]).
7. 예비창업자가 생존 전망의 분해, 15개월·39개월 생존곡선, 개선 시나리오와 후보 위치, 지원사업 판정을 확인한다.
8. 예비창업자가 리포트를 대출 상담 신청에 첨부한다. 리포트가 심사 큐에 들어간다.

**확장**
- **1a. 군위군을 고른다**
  - 1a1. 시스템이 [[#UC-S1]]의 확장 1c에 따라 편입 이전 이력이 없음을 고지하고 분리 집계한다.
- **1b. 외부 네트워크가 없다 (현장 시연·폐쇄망)**
  - 1b1. 시스템이 3·4를 로컬 스냅샷만으로 수행한다. 흐름은 달라지지 않는다.
  - 1b2. 5는 사전 적재한 공고 목록으로 수행하고, 목록을 적재한 시점을 판정 결과에 표시한다([[#UC-S5]] 확장 1a).
  - 1b3. 6의 앵커링은 로컬 원장에 기록한다.
- **3a. 3~6이 10초를 넘긴다**
  - 3a1. 시스템이 지금 수행 중인 단계를 화면에 표시한다.
- **3b. 코호트 집계가 실패한다 (상위 분류로 올려도 표본 부족)**
  - 3b1. 시스템이 리포트를 발급하지 않고, 이 조건으로는 비교할 표본이 부족하다고 알린다. 유스케이스 종료.
- **4a. 예산 안에서 나은 대안이 2개 미만이다**
  - 4a1. 시스템이 찾은 만큼만 리포트에 담고 그 사실을 표시한다([[#UC-S2]] 확장 4a).
- **7a. 조건을 바꿔 다시 평가한다**
  - 7a1. 예비창업자가 1로 돌아간다.
  - 7a2. 시스템이 이전 리포트를 지우지 않고 남겨 두 리포트를 나란히 비교할 수 있게 한다.
- **8a. 첨부하지 않고 끝낸다**
  - 8a1. 리포트는 식별번호로 남아 이후 창구에서 불러올 수 있다([[#UC-H2]] 확장 1a).

#### UC-H2 상담 중에 고객과 리포트를 함께 검토한다

| 항목 | 내용 |
|---|---|
| 범위 | 창업 신용 리포트 엔진 |
| 수준 | 사용자 목표 |
| 주 액터 | 창구 직원 |
| 이해관계자와 관심사 | **창구 직원**: 해당 지역 상권을 몰라도 근거를 갖고 상담을 끝내고 싶다.<br>**고객(예비창업자)**: 숫자가 왜 그렇게 나왔는지 이해하고 싶다.<br>**심사역**: 창구에서 고객에게 설명한 근거와 자기가 검토할 근거가 같기를 바란다. |
| 사전조건 | 대상 지역 스냅샷이 적재돼 있다. 창구 직원이 창구용 화면에 접근할 수 있다. |
| 최소 보장 | 상담이 중간에 끊겨도 입력한 조건과 발급된 리포트는 남는다. |
| 성공 보장 | 고객과 함께 본 리포트가 심사 큐에 등록된다. 이후 누가 열어도 같은 근거 경로가 나온다. |
| 트리거 | 창업자금 상담 고객이 창구에 온다. |
| 패키지 | 상담·심사 |
| 포함(include) | [[#UC-S1]], [[#UC-S2]], [[#UC-S5]], [[#UC-S3]], [[#UC-S4]] |
| 확장점(extension point) | — |
| 일반화 | — |

**기본 흐름**
1. 창구 직원이 고객의 업종·지역·예산·면적을 선택형 입력으로 고른다.
2. 시스템이 코호트 생존을 집계하고([[#UC-S1]]) 개선 시나리오를 탐색하고([[#UC-S2]]) 지원사업 자격을 판정한 뒤([[#UC-S5]]) 리포트를 조립한다([[#UC-S3]]).
3. 창구 직원이 리포트를 고객과 함께 본다.
4. 고객이 근거를 묻는 보정 항목을 창구 직원이 선택한다.
5. 시스템이 그 수치의 근거 경로를 펼친다([[#UC-S4]]).
6. 창구 직원이 개선 시나리오와 지원사업 판정을 고객과 검토한다.
7. 창구 직원이 리포트를 심사 큐에 등록한다.

**확장**
- **1a. 고객이 이미 발급받은 리포트의 식별번호를 가져왔다**
  - 1a1. 창구 직원이 식별번호로 리포트를 불러온다.
  - 1a2. 2를 건너뛰고 3부터 진행한다.
- **1b. 식별번호에 해당하는 리포트가 없다**
  - 1b1. 시스템이 찾을 수 없다고 알린다. 1로 돌아간다.
- **5a. 같은 리포트에서 같은 수치를 다시 선택한다**
  - 5a1. 시스템이 같은 경로를 내놓는다([[#UC-S4]] 확장 1a).
- **7a. 고객이 신청하지 않기로 한다**
  - 7a1. 창구 직원이 큐에 등록하지 않고 식별번호만 고객에게 안내한다. 유스케이스 종료.

#### UC-H3 창업 신용 리포트를 심사한다

| 항목 | 내용 |
|---|---|
| 범위 | 창업 신용 리포트 엔진 |
| 수준 | 사용자 목표 |
| 주 액터 | 심사역 |
| 이해관계자와 관심사 | **심사역**: 사업 이력 없는 신청자를 근거로 판단하되, 그 근거의 시점과 문서의 원본 여부를 확인하고 싶다.<br>**신청자**: 계획 자체로 평가받고 싶다.<br>**iM뱅크**: 판단 근거를 나중에 다시 확인할 수 있기를 바란다. |
| 사전조건 | 심사 큐에 리포트가 하나 이상 있다. |
| 최소 보장 | 원본 검증을 통과하지 못한 리포트를 원본인 것처럼 보여주지 않는다. |
| 성공 보장 | 심사역이 근거 분해·근거 경로·기준일·한계 고지·원본 검증 결과를 모두 본 상태에서 판단한다. |
| 트리거 | 심사역이 심사 큐를 연다. |
| 패키지 | 상담·심사 |
| 포함(include) | [[#UC-S4]], [[#UC-S7]] |
| 확장점(extension point) | — |
| 일반화 | — |

**기본 흐름**
1. 심사역이 심사 큐를 열고 리스크 등급이나 접수일로 정렬한다.
2. 심사역이 리포트를 연다.
3. 시스템이 리포트의 원본 여부를 검증해 결과를 리포트 상단에 표시한다([[#UC-S7]]).
4. 심사역이 생존 전망과 업종 기준선·경쟁 밀도 보정·지역 보정의 분해를 확인한다.
5. 심사역이 보정 수치를 선택하고, 시스템이 근거 경로를 펼친다([[#UC-S4]]).
6. 심사역이 원천 기준월과 생존율 산출에 쓴 과거 분기를 확인한다.
7. 심사역이 한계 고지를 확인한다.
8. 심사역이 보증 연계·한도 조정·승인 중 하나로 판단한다. 판단 기록은 이 시스템의 범위 밖이다.

**확장**
- **3a. 발급 이후 수정됐다고 판정된다**
  - 3a1. 시스템이 경고를 표시한다.
  - 3a2. 심사역이 원본 재발급을 요청한다. 유스케이스 종료.
- **3b. 검증 불가로 판정된다 (검증 해시 없음·원장 기록 없음)**
  - 3b1. 시스템이 검증 불가 사유를 표시한다. 4부터 그대로 진행하되 심사역은 이 사실을 판단에 반영한다.
- **4a. 코호트가 상위 분류로 폴백된 리포트다**
  - 4a1. 시스템이 폴백 단계와 낮은 신뢰 수준을 눈에 띄게 표시한다.

#### UC-H4 평가를 다른 시도로 전환한다

| 항목 | 내용 |
|---|---|
| 범위 | 창업 신용 리포트 엔진 |
| 수준 | 사용자 목표 |
| 주 액터 | 운영 담당자 |
| 이해관계자와 관심사 | **운영 담당자**: 지역마다 다시 만들지 않고 켜고 싶다.<br>**대상 지역 창구 직원**: 대구와 같은 방식으로 쓰고 싶다. |

- **1c. 입력 지역이 군위군이다**
  - 1c1. 시스템이 2023년 7월 편입 이전 스냅샷에는 군위군이 없다는 사실을 결과에 담는다.

- **2a. 외부 네트워크가 없다**
  - 2a1. 모든 대조를 로컬 스냅샷에서 수행하므로 흐름이 달라지지 않는다.

#### UC-S8 스냅샷을 적재한다

| 항목 | 내용 |
|---|---|
| 범위 | 창업 신용 리포트 엔진 |
| 수준 | 하위기능 |
| 주 액터 | 시스템 (호출자: UC-H4) |
| 이해관계자와 관심사 | **운영 담당자**: 적재가 반쯤 실패해 틀린 결과가 나가는 일이 없기를 바란다.<br>**심사역**: 리포트의 기준월이 실제 원천 기준월과 같기를 바란다. |
| 사전조건 | 대상 지역 식별자가 설정돼 있다. |
| 최소 보장 | 적재가 끝나기 전의 불완전한 데이터로 평가가 수행되지 않는다. 실패하면 이전 스냅샷이 유지된다. |
| 성공 보장 | 대상 지역의 현재 스냅샷과 코호트 비교에 필요한 과거 분기 스냅샷이 로컬에 적재되고, 각각의 원천 기준월이 기록되며, 지식그래프가 구성된다. |
| 트리거 | 호출자가 지역 전환을 요청한다. |
| 패키지 | 운영 |
| 포함(include) | — |
| 확장점(extension point) | — |
| 일반화 | — |

**기본 흐름**
1. 시스템이 상가(상권)정보 API로 대상 지역의 현재 점포 전량을 페이지 단위로 받는다. 대구 기준 1,000건씩 119회다.
2. 시스템이 코호트 비교에 쓸 과거 분기 스냅샷 파일을 받아 대상 지역만 추린다.
3. 시스템이 API 응답 필드와 파일 필드의 대응을 확인한다. 둘은 같은 39개 항목이지만 이름이 다르다(API는 영문 키 `lnoCd`, 파일은 한글 헤더 `지번코드`).
4. 시스템이 점포·건물·지번·행정동·업종 관계로 지식그래프를 구성한다.
5. 시스템이 적재를 완료로 표시하고 각 스냅샷의 원천 기준월을 기록한다.

**확장**
- **1a. 일일 트래픽 한도에 걸린다**
  - 1a1. 시스템이 받은 페이지까지 보관하고 다음 날 이어받는다. 5에 이르기 전까지 평가는 이전 스냅샷으로 수행된다.
- **2a. 분기 파일을 받지 못한다**
  - 2a1. 시스템이 적재를 중단하고 원인을 알린다. 이전 스냅샷을 유지한다.
- **3a. 필드 대응이 맞지 않는다 (분기 사이 컬럼 추가·삭제)**
  - 3a1. 시스템이 적재를 중단하고 대응이 깨진 필드를 알린다. 이전 스냅샷을 유지한다.

**연관**: [[IMBC-PRD-001#R2]], [[IMBC-PRD-001#N4]], [[IMBC-PRD-001#N5]] / [[IMBC-SCN-001#S5]]

## 5. 미결사항

- [ ] **[[IMBC-PRD-001#R3]] 내부 충돌** — 인수기준 "최소 2개 이상의 개선 시나리오"와 "예산 제약을 위반하는 대안은 제시하지 않는다"가 예산 안 대안이 부족할 때 동시에 지켜지지 않는다. 같은 PRD 4.3의 성공지표는 "95% 이상에서 2개 이상"이라 100%를 요구하지 않는다. [[#UC-S2]] 확장 4a에서 예산 제약 우선으로 정했고, PRD 인수기준 조정이 필요하다

- [ ] **[[IMBC-PRD-001#R6]] 판정 불가 영역** — [[IMBC-PRD-001#R1]]이 입력을 코호트 매칭 축으로 한정해 연령이 없다. 청년 대상 지원사업은 대부분 연령 조건이 있어 자격을 판정할 수 없다. [[#UC-S5]] 확장 3a에서 "판정 불가"로 처리했으나, R1에 선택 입력으로 연령을 둘지 R6의 기대치를 낮출지 PRD에서 정해야 한다
- [ ] [[#UC-S2]]의 후보 위치는 경쟁 조건을 만족하는 **좌표**이지 임대 가능한 매물이 아니다. 공실 데이터가 없다. 리포트에서 이 차이를 어떻게 표기할지 정해야 한다
- [ ] [[#UC-S4]] 확장 1a를 지키려면 리포트 기준월의 스냅샷을 보존하거나 근거 경로를 리포트와 함께 저장해야 한다. INFRA·DOM에서 정한다
- [ ] [[#UC-S1]] 확장 1b(대분류로도 표본 60건 미만)가 실제로 어떤 조건에서 발생하는지 확인 필요
